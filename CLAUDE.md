# Golubev Consulting — golubev-consulting.ru

Сайт консалтинга Артура Голубева. Общий контекст (автоматизация, cron, Telegram) — в `~/sites/CLAUDE.md`, он подхватывается автоматически. Здесь только специфика проекта.

- **Репозиторий:** `golubev-artur/golubev-growth-engine` (SSH)
- **Домен:** golubev-consulting.ru (GitHub Pages, `public/CNAME`)
- **Стек:** Vite + React 18 + TS + Tailwind + shadcn/ui, роутинг `react-router-dom`, SEO через `react-helmet-async`

## Команды

```bash
npm run dev       # локальный сервер
npm run build     # vite build + scripts/generate-blog-pages.mjs
npm run test      # vitest
npm run lint
```

`npm run build` обязательно прогоняет `generate-blog-pages.mjs` — он делает статические HTML-страницы для каждого поста (OG-теги, meta) поверх `dist/index.html`. Без него посты теряют превью в соцсетях и хуже индексируются.

## Блог

**Данные:** `src/data/blog.ts` — один большой массив `blogPosts` (~1 МБ, 100+ постов). Файл большой: читай частями через `offset`/`limit`, а не целиком.

```ts
export interface BlogPost {
  slug: string;      // уникальный, английский kebab-case
  title: string;     // русский, включает ключевой запрос
  excerpt: string;   // 1-2 предложения
  date: string;      // YYYY-MM-DD
  category: string;  // из списка ниже
  readTime: string;  // '8 мин'
  image: string;     // имя переменной из шапки файла
  content: string;   // сама статья
}
```

**Новый пост добавляется ПЕРВЫМ элементом массива** — сразу после `export const blogPosts: BlogPost[] = [`. Сортировки по дате в рантайме нет, порядок в файле = порядок на сайте.

### Категории (только эти)
`Продажи и CRM` · `Управление и стратегия` · `Автоматизация` · `Персонал и команда` · `Клиентский сервис` · `Маркетинг` · `Бизнес-процессы` · `Финансы` · `Юридические услуги` · `Стратегические сессии`

### Картинки
Переменные объявлены в начале `blog.ts`, в поле `image` пишется **имя переменной**, не строка:
`arthurOffice1`, `arthurOffice2`, `arthurOffice4`, `arthurOffice5`, `blogCrm`, `blogOkr`, `blogAutomation`, `blogHr`, `blogNps`, `blogAi`, `serviceStrategy`, `arthurMain`

**Картинка нового поста не должна совпадать с картинками 5 предыдущих постов.** Список
блога выводится по 6 постов на страницу (`POSTS_PER_PAGE` в `src/pages/Blog.tsx`), и на
одной странице двух одинаковых фото быть не должно. Картинок в пуле 12 - выбор всегда есть.

Подстраховка на случай нарушения: `withUniqueImages` (`src/lib/uniquePageImages.ts`)
подменяет повтор на свободную картинку из пула при выводе списка. Подмена детерминированная
(хэш от slug) и только в карточках - на странице статьи остаётся её собственная картинка.
Тесты в `src/test/blogImages.test.ts` проверяют отсутствие дублей на каждой странице.
Это защита от случайности, а не повод игнорировать правило выше: в данных картинки
должны быть разными сами по себе.

### Правила текста
- Объём **1000-1300 слов**, заголовки `##`.
- Стиль — Артур Голубев: эксперт-консультант с 12+ годами практики, прямой и практичный тон, конкретные примеры и цифры.
- Ключевой запрос обязан войти в **H1, первый абзац и один из H2**.
- **2-3 внутренние ссылки** — обычным текстом со слешем в скобках, НЕ markdown:
  `«Подробнее в нашем направлении по продажам и CRM (/services/sales-crm)»`
- **Длинное тире (—) запрещено.** Только дефис (-). Есть автозамена в скрипте, но лучше писать сразу правильно.
- Не дублируй темы: сверься со списком существующих `slug` в файле.

### Что обновляется вместе с постом
1. `src/data/blog.ts` — сам пост
2. `public/sitemap.xml` — `<url>` перед `</urlset>`, `priority 0.7`, `changefreq monthly`
3. `public/rss.xml` — не руками: `node scripts/update-rss.mjs` (сборка ленту не трогает)
4. IndexNow → отправляется сам, job `indexnow` в `deploy.yml` после успешного деплоя
5. `content/blog-plan.md` - тема отмечается опубликованной: `[ ]` → `[x]`

Коммит: `Блог: [название поста]`.

## План тем

Темы на месяц вперёд лежат в `content/blog-plan.md`: дата слота, категория, тема,
предполагаемый slug и статус (`[ ]` свободна / `[x]` опубликована).

**Постоянные правила - действуют без напоминаний, при любом изменении плана:**

1. **График** - пн / ср / пт. Один слот - один пост. План на месяц = 13-14 тем.
2. **Пост пишется непосредственно перед публикацией**, не заранее. В плане - только темы;
   готовых текстов впрок не держим.
3. **Когда неиспользованных тем остаётся 2 или меньше - сразу составляется новый план на
   месяц** и дописывается в `content/blog-plan.md` новым разделом. Ждать, пока темы
   закончатся полностью, нельзя.
4. **Категории добираются по отставанию.** Перед составлением плана считаем распределение
   постов по категориям в `src/data/blog.ts` и отдаём слоты тем направлениям, которых меньше
   всего. Блог тянет SEO-трафик на `/services/*`, поэтому направления услуг не должны
   оставаться без статей. Ни одна категория не берёт больше 3 слотов в месяце.
5. **Тема не дублирует существующие.** Перед внесением в план сверяемся со списком `slug`
   и заголовков в `src/data/blog.ts` - в том числе по смыслу, а не только по формулировке.
6. Опубликовав пост, отмечаем тему `[x]` в том же коммите.

**Оговорка про автопубликацию.** Скрипт `~/scripts/publish-blog-post.sh` берёт темы из
своего `~/scripts/blog-keywords.txt` и этот план не читает (он вообще игнорирует CLAUDE.md).
Пока список из плана не перенесён в тот файл, cron публикует по своей очереди тем.
Готовый к переносу список - в конце `content/blog-plan.md`.

## Кто публикует посты

1. **Локальный cron** — `~/scripts/publish-blog-post.sh` на машине владельца, пн/ср/пт 06:00.
   Требует включённой машины и залогиненного `claude`. С 26.08.2026 не публиковал ничего.
2. **Расписание в облаке** — Routine `trig_01STWTfyjcmVNoNUVBfCksB5`, пн/ср/пт 06:00 МСК.

**Важно про облачное расписание.** Оно привязано к конкретной сессии
(`session_01ASMQmUcLeGyUHAK6Z5k3Zh`), в которой репозиторий подключён как источник.
Первая версия поднимала на каждое срабатывание ЧИСТУЮ сессию — и это не работало:
такая сессия стартует без репозитория (тег `config:no-git-repo`), завершалась за
15-120 секунд, ничего не опубликовав, и помечалась как «успешная». Так было потеряно
время с 09.09 по 09.10.2026: расписание срабатывало 13 раз, постов не вышло ни одного.
Если будешь пересоздавать Routine — не делай `create_new_session_on_fire`, привязывай
к сессии с подключённым репозиторием.

**Защита от дубля.** Оба публикатора перед работой смотрят дату верхнего поста в
`blog.ts`: если она сегодняшняя, публикация пропускается. Выключать cron не требуется.

**Сторож.** `.github/workflows/blog-watchdog.yml` раз в сутки проверяет дату последнего
поста и при тишине дольше 4 дней шлёт тревогу в Telegram. Он работает на GitHub и не
зависит ни от Claude, ни от машины владельца: его задача — чтобы поломка публикации
больше никогда не прошла незамеченной.

## Автопубликация (локальный скрипт)

`~/scripts/publish-blog-post.sh`, cron **пн/ср/пт в 06:00**. Порядок работы:

1. Лок + проверка «сегодня уже был пост?» (по дате коммита в `blog.ts`)
2. `git pull --rebase`
3. Берёт первый неиспользованный запрос из `~/scripts/blog-keywords.txt`; если осталось ≤3 — генерирует 20 новых
4. Запускает `claude --model claude-opus-4-8 -p "..."` с промптом-инструкцией (шаги 1-7)
5. **Проверка успеха:** верхний пост в `blog.ts` должен иметь сегодняшнюю дату. Не совпало или в выводе признак разлогина → откат `git checkout`, алерт в TG, выход
6. Автозамена `—` → `-`
7. Перегенерация RSS → коммит → push с retry
8. IndexNow (Yandex + Bing)
9. `sleep 240`, затем верификация: пуш прошёл · slug есть в RSS · `lastBuildDate` сегодняшняя · slug есть в sitemap
10. Итог в TG: ✅ с ссылкой либо 🚨 со списком проблем

Промпт для генерации поста живёт внутри скрипта (строки ~144-186). **Если нужно поменять правила написания постов — правится он, а не этот файл:** автозапуск явно игнорирует CLAUDE.md.

## Telegram

**Лиды идут через серверный прокси, не напрямую.** `src/lib/telegram.ts` шлёт POST на `https://api.golubev-consulting.ru/lead`; сервер (`~/sites/golubev-consulting/client-api/server.js`) пересылает в Telegram.

Причина: `api.telegram.org` заблокирован у посетителей из РФ, прямой `fetch` из браузера не проходит. **Не переписывай на прямой вызов Telegram API** — заявки перестанут доходить. Бонусом токен бота не попадает в бандл.

Формы, использующие `sendToTelegram`: `ContactSection`, `ContactFormModal`, `PresentationGate`, `Booking`.

**Ошибку отправки заявки нельзя глушить.** Раньше во всех четырёх формах стоял пустой
`catch`, и посетитель видел «Заявка отправлена» даже когда прокси был недоступен: заявка
терялась молча, и ни он, ни мы об этом не узнавали. Правило: при неудаче показать
`leadErrorToast` из `src/lib/leadError.ts`, НЕ показывать экран успеха, НЕ сбрасывать
форму и не закрывать модальное окно - посетитель должен увидеть ошибку, телефон для
связи и иметь возможность отправить повторно.

**Дублирование заявок на почту.** В `client-api/` лежит модуль `lead-email.js`:
пишет каждую заявку в `leads.log` и шлёт письмо на почту владельца. Нужен потому,
что Telegram - единственный канал доставки, и при его недоступности заявка
пропадала без следа. Модуль не бросает ошибок наружу и при отсутствии настроек
просто молчит, поэтому подключение не может сломать отправку в Telegram.

**Сервер приёма заявок в этом репозитории не лежит** - он на машине владельца,
`~/sites/golubev-consulting/client-api/server.js`. Отсюда его править и
перезапускать нельзя: модуль и инструкция по подключению - в `client-api/README.md`,
применять нужно на той машине.

**Уведомления о постах** — см. `~/sites/CLAUDE.md`. Приходят из двух мест: из скрипта публикации (после верификации) и из job `notify` в `.github/workflows/deploy.yml` (тот парсит diff `blog.ts` на новые `slug:`).

## IndexNow и Яндекс

Отправка идёт в два эндпоинта: `yandex.com/indexnow` и общий `api.indexnow.org/indexnow`.

**С 12.10.2026 эндпоинт Яндекса не отвечает**: обрывает соединение без ответа
(в curl - `HTTP/2 stream INTERNAL_ERROR`, код 000). 10.09.2026 он отвечал 200,
то есть поведение изменилось на его стороне. Добавление User-Agent, HTTP/1.1
и трёх попыток не помогло - похоже на блокировку по IP раннеров GitHub.

Это не критично: `api.indexnow.org` принимает (HTTP 200), а участники IndexNow,
включая Яндекс, обмениваются присланными адресами между собой. Эндпоинт Яндекса
оставлен в коде - он может заработать обратно, неудача видна как warning в логе.

Надёжный ручной канал для Яндекса - Вебмастер, раздел «Индексирование →
Переобход страниц». Не трать время на отладку кода: проблема внешняя.

## Название компании

В текстах для поисковиков и посетителей бренд пишется **по-русски: «Голубев Консалтинг»**.
Сайт и запросы русскоязычные - в выдаче приписка должна совпадать с тем, как бренд
набирают. Латиница `Golubev Consulting` осталась только как `alternateName` в
микроразметке (`index.html`, `Seo.tsx`, `generate-blog-pages.mjs`) - это подсказка
поисковику, что оба написания об одной компании. Отдельно живёт логотип: в шапке и
на баннерах он набран капсом «ГОЛУБЕВ КОНСАЛТИНГ», это графика, её не трогаем.

**Приписка бренда в title** добавляется по двум правилам, одинаковым в пререндере
(`pageTitle` в `scripts/generate-blog-pages.mjs`) и в рантайме (`Seo.tsx`):
заголовок длиннее 41 символа - приписки нет (иначе выдача обрежет сам заголовок);
бренд уже в заголовке - второй раз не добавляем. **Логика в двух местах должна
совпадать**, иначе робот видит один title в HTML и другой после отрисовки.

**Количество направлений нигде не пишется цифрой руками** - берётся из
`services.length` (`src/data/services.ts`). До 12.10.2026 на сайте одновременно
стояли 7, 8, 9 и 10 - при реальных десяти.

## Деплой

`.github/workflows/deploy.yml`, триггер — push в `main`. Джобы: `build` (npm install → npm run build → детект новых постов в diff) → `deploy` (GitHub Pages) → `notify` (TG, только если найдены новые посты).

`fetch-depth: 2` в checkout нужен именно для `git diff HEAD~1 HEAD` в детекте постов — не уменьшай.
